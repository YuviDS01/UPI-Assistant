# AI Agentic UPI Payment Assistant (Prototype)

A conversational AI assistant that manages recurring UPI payments
(mandates), detects new payments, checks them against a deterministic
policy engine, and routes anything outside policy to a human approval
step — while a non-custodial `MockUPIProvider` stands in for real money
movement.

**Not a production banking system.** See `docs/security.md` for the full
list of guardrails and known limitations.

## The USP: pause without cancelling

UPI AutoPay subscriptions are normally binary — on, or cancelled through a
multi-step bank/UPI-app flow most people never bother with. This assistant
adds a third state: **paused**. Say "pause my Netflix payment for 2
months" and the scheduler silently skips those charges — the underlying
bank-side mandate authorization is never touched, so resuming later needs
no re-approval, no OTP, nothing. See `docs/architecture.md` §0 and
`docs/agent-workflows.md`.

## Architecture

Four layers: **Client** (React) → **Backend** (FastAPI, the sole authority
over money movement) → **Agent** (Claude + LangChain + LangGraph,
understands but never authorizes) → **Payment** (swappable provider
interface, `MockUPIProvider` today). Full diagrams: `docs/architecture.md`.

## Tech stack

Frontend: React, TypeScript, Vite, Tailwind CSS.
Backend: Python, FastAPI, Pydantic, SQLAlchemy 2.x, Alembic.
Database: PostgreSQL. Cache/checkpointing: Redis + LangGraph's Postgres checkpointer.
AI: Claude API, LangChain, LangGraph. Scheduler: APScheduler (behind a swappable interface).
Testing: Pytest, HTTPX. Dev: Docker, Docker Compose.

## Setup

### Prerequisites
Docker Desktop, Git. (Node/Python locally are only needed if you want to
run the frontend or backend outside Docker.)

### Environment variables
```powershell
Copy-Item .env.example .env
Copy-Item frontend\.env.example frontend\.env
```
Fill in `ANTHROPIC_API_KEY` in `.env` (required from Phase 8 onward — chat
won't work without it) and `VITE_DEV_USER_ID` in `frontend/.env` (get it
after seeding, step 3 below).

### Database setup
```powershell
docker compose up --build -d
docker compose exec backend alembic upgrade head
docker compose exec backend python -m app.core.seed
```

### Running everything
```powershell
docker compose up --build -d
```
- Backend: http://localhost:8000 (docs at `/docs`, auto-generated by FastAPI)
- Frontend: http://localhost:5173
- Postgres: localhost:5432 · Redis: localhost:6379

### Running tests
```powershell
docker compose exec backend pytest -v
```
77 tests across unit, integration, and agent suites. Set
`ENABLE_SCHEDULER=false` in `.env` while running tests to avoid a
background job racing with test data.

### Demo instructions
See `docs/demo.md` for the three full walkthroughs (chat-created mandate →
scheduled execution; new payment → approval → execution; pause a live
subscription → scheduler skips it → resume).

### Mock payment mode (default)
`PAYMENT_PROVIDER=mock` in `.env`. No real money, ever. Two magic amounts
for deterministic demos: `66666` always fails, `77777` always comes back
`PENDING`.

### Paytm sandbox mode
`PAYMENT_PROVIDER=paytm` — requires real credentials (`PAYTM_MID`,
`PAYTM_MERCHANT_KEY`) and, currently, replacing the checksum placeholder
in `app/payment_providers/paytm_checksum.py` with Paytm's official
utility before it does anything beyond structural checks. See
`docs/architecture.md` Phase 13 notes for exactly what's scaffolded vs.
verified.

### Security limitations & why this isn't production
`docs/security.md` — read this before assuming any part of this is
production-ready. Short version: single dev-mode auth header, mock
payment provider, no compliance review, but the *architectural pattern*
(deterministic backend as sole authority over money, LLM strictly
advisory) is meant to generalize to a real system.
